## 1. 引言

UNIX 是一个通用、多用户、交互式操作系统，运行于 DEC PDP-11/40 和 11/45 计算机。它提供若干即使在更大系统中也很少见的功能，包括：

1. 支持可卸载卷的层次文件系统；
2. 兼容的文件、设备和进程间 I/O；
3. 启动异步进程的能力；
4. 可按用户选择的系统命令语言；
5. 100 多个子系统，包括十几种语言。

本文讨论文件系统的性质与实现，以及用户命令接口。

UNIX 已有三个版本。最早版本（约 1969–1970 年）运行在 DEC PDP-7 和 PDP-9 上；第二版运行在没有存储保护的 PDP-11/20 上。本文只描述 PDP-11/40 和 /45 系统，因为它更新，而且它与旧 UNIX 系统的许多差异，源自对被发现不足或缺失特性的重新设计。

自 1971 年 2 月 PDP-11 UNIX 投入运行以来，约有 40 个安装投入使用；它们通常比本文描述的系统小。其中大多数用于专利申请和其它文本材料的准备与格式化、贝尔系统内各种交换机的故障数据收集与处理，以及电话服务订单的记录与检查。我们自己的安装主要用于操作系统、语言、计算机网络和其它计算机科学主题研究，也用于文档准备。

也许 UNIX 最重要的成就，是证明一个用于交互式使用的强大操作系统，无论在设备还是人力上都不必昂贵：UNIX 可运行在低至 40,000 美元的硬件上，主系统软件开发花费不到两个人年。然而，UNIX 包含许多即使在更大系统中也很少提供的功能。不过，我们希望 UNIX 用户会发现，系统最重要的特征是简单、优雅和易用。

除系统本身外，UNIX 下的主要程序包括：汇编器、基于 QED 的文本编辑器、链接加载器、符号调试器、一种类似 BCPL 但具有类型和结构的语言（C）的编译器、某种 BASIC 方言的解释器、文本格式化程序、Fortran 编译器、Snobol 解释器、自顶向下编译—编译器（TMC）、自底向上编译—编译器（YACC）、套用信函生成器、宏处理器（M6）和置换索引程序。此外还有大量维护、实用、娱乐和新奇程序。所有这些程序都是在本地编写的。值得注意的是，系统完全自支持：所有 UNIX 软件都在 UNIX 下维护；同样，UNIX 文档也由 UNIX 编辑器和文本格式化程序生成和格式化。

## 2. 硬件与软件环境

我们的 UNIX 安装所运行的 PDP-11/45 是一台 16 位字长（8 位字节）、具有 144K 字节核心内存的计算机；UNIX 占用 42K 字节。不过，这个系统包含大量设备驱动程序，并为 I/O 缓冲区和系统表分配了宽裕空间；而一个能够运行上述软件的最小系统，总共只需约 50K 字节核心内存。

PDP-11 配有 1M 字节固定头磁盘，用于文件系统存储和交换；四个移动头磁盘驱动器，每个在可卸载磁盘盒上提供 2.5M 字节；以及一个使用可卸载 40M 字节磁盘组的移动头磁盘驱动器。此外还有高速纸带读写器、九轨磁带和 DEctape（一种可寻址并重写单条记录的磁带设施）。除控制台打字机外，还有 14 个可变速度通信接口，连接到 100 系列数传机，以及一个主要用于把打印输出假脱机到共用行式打印机的 201 数传机接口。还有若干专用设备，包括 Picturephone 接口、语音应答装置、语音合成器、照相排版机、数字交换网络，以及一台在 Tektronix 611 存储管显示器上生成向量、曲线和字符的卫星 PDP-11/20。

UNIX 软件的大部分用上述 C 语言编写。早期操作系统版本用汇编语言编写，但在 1973 年夏天，系统用 C 重写。新系统规模约比旧系统大三分之一。由于新系统不仅更容易理解和修改，而且包含许多功能改进，包括多道程序设计以及在多个用户程序间共享可重入代码的能力，我们认为这种规模增长完全可接受。

## 3. 文件系统

UNIX 最重要的作用是提供文件系统。从用户观点看，有三类文件：普通磁盘文件、目录和特殊文件。

### 3.1 普通文件

文件包含用户放入其中的任何信息，例如符号程序或二进制（目标）程序。系统不期望文件具有任何特定结构。文本文件只是字符串，行由换行符分隔。二进制程序是程序开始执行时在核心内存中呈现的字序列。少数用户程序会操作结构更强的文件：汇编器生成、加载器期望特定格式的目标文件。然而，文件结构由使用它们的程序控制，而不是由系统控制。

### 3.2 目录

目录提供文件名与文件本身之间的映射，从而在整个文件系统上诱导出结构。每个用户有自己的文件目录；他也可以创建子目录，以便把一组文件方便地放在一起处理。目录的行为与普通文件完全相同，只是非特权程序不能写入目录，因此系统控制目录内容。不过，任何具有适当权限的人都可以像读取其它文件一样读取目录。

系统维护若干供自身使用的目录。其中之一是根目录。系统中的所有文件都可以通过沿着目录链追踪路径找到，直到到达所需文件。这种搜索的起点通常是根目录。另一个系统目录包含提供给一般使用的所有程序，即所有命令。但如下所述，程序并不必须驻留在该目录中才能执行。

文件以 14 个或更少字符的序列命名。当向系统指定文件名时，它可以是路径名形式，即由斜杠 `/` 分隔的目录名序列，最后以文件名结尾。如果序列以斜杠开头，搜索从根目录开始。名字 `/alpha/beta/gamma` 使系统在根目录中搜索目录 alpha，然后在 alpha 中搜索 beta，最后在 beta 中找到 gamma。gamma 可以是普通文件、目录或特殊文件。作为极限情况，名字 `/` 指根本身。

不以 `/` 开头的路径名，使系统从用户当前目录开始搜索。因此名字 `alpha/beta` 指定当前目录的子目录 alpha 中名为 beta 的文件。最简单的名字例如 alpha，指当前目录中的文件。另一个极限情况是空文件名指当前目录。

同一个非目录文件可以出现在多个目录中，并可能使用不同名字。这个特性称为**链接**（linking）；文件的目录项有时称为 link。UNIX 与允许链接的其它系统不同之处在于：指向一个文件的所有 link 具有同等地位。也就是说，文件并不“存在于某个特定目录中”；文件的目录项只包含它的名字和指向描述该文件信息的指针。因此，文件独立于任何目录项而存在，尽管实践中文件会随着最后一个 link 的消失而消失。

每个目录至少有两个项。每个目录中的名字 `.` 指目录自身。因此程序可以在不知道完整路径名的情况下，以名字 `.` 读取当前目录。按约定，名字 `..` 指包含该目录的目录，也就是创建它的目录。

目录结构被约束为有根树形式。除特殊项 `.` 和 `..` 外，每个目录必须作为恰好一个其它目录（即其父目录）中的项出现。原因是为了简化遍历目录子树程序的编写，更重要的是避免层次结构各部分被分离。如果允许任意链接到目录，就很难检测根到某目录的最后一条连接何时被切断。

### 3.3 特殊文件

特殊文件构成 UNIX 文件系统最不寻常的特性。UNIX 支持的每个 I/O 设备至少与一个这样的文件关联。特殊文件像普通磁盘文件一样读写，但读写请求会导致相关设备被激活。每个特殊文件都有一个项位于 `/dev` 目录中，不过也可以像普通文件一样链接到这些文件之一。例如，要打纸带，可以写文件 `/dev/ppt`。每条通信线路、每个磁盘、每个磁带驱动器以及物理核心内存都有特殊文件。当然，活动磁盘和核心特殊文件受到保护，防止任意访问。

以这种方式处理 I/O 设备有双重优势：文件和设备 I/O 尽可能相似；文件名和设备名具有相同的语法与意义，因此期望文件名作为参数的程序可以传入设备名。最后，特殊文件受到与普通文件相同的保护机制约束。

### 3.4 可卸载文件系统

虽然文件系统根总是存放在同一设备上，但整个文件系统层次不必驻留在该设备上。有一个 `mount` 系统请求，它有两个参数：一个已有普通文件的名字，以及一个直接访问特殊文件的名字，该特殊文件关联的存储卷（例如磁盘组）应具有独立文件系统结构，包含自身的目录层次。`mount` 的效果是：此后对这个此前为普通文件的引用，改为指向可卸载卷上文件系统的根目录。实际上，`mount` 用一整棵新子树（可卸载卷上的层次结构）替换层次树中的一个叶子（普通文件）。挂载之后，可卸载卷上的文件与永久文件系统中的文件几乎没有区别。例如在我们的安装中，根目录驻留在固定头磁盘上，包含用户文件的大磁盘驱动器由系统初始化程序挂载；四个较小磁盘驱动器可由用户挂载自己的磁盘组。可挂载文件系统通过在其对应特殊文件上写入生成。有一个实用程序可创建空文件系统，也可以直接复制现有文件系统。

不同设备上文件受到相同处理的规则只有一个例外：两个文件系统层次之间不能存在链接。这一限制是为了避免复杂的簿记工作，否则在可卸载卷最终卸载时，必须保证移除这些链接。特别是，在所有文件系统根目录中，无论是否可卸载，名字 `..` 都指目录自身，而不是父目录。

### 3.5 保护

虽然 UNIX 的访问控制方案很简单，但它有一些不寻常特性。系统每个用户被分配一个唯一用户标识号。文件创建时，会被标记所有者用户 ID。新文件还带有一组 7 个保护位，其中 6 位分别指定文件所有者和其他用户的读、写、执行权限。

如果第 7 位开启，则每当该文件作为程序执行时，系统临时把当前用户标识改为文件创建者的标识。这种用户 ID 改变只在执行该程序期间有效。set-user-ID 特性提供了特权程序，它们可以使用其它用户无法访问的文件。例如，一个程序可以保存记账文件，该文件既不应被其它人读取，也不应被其它人修改，只能由程序本身访问。如果该程序的 set-user-ID 位开启，它就可以访问该文件，尽管调用该程序的用户所调用的其它程序可能被禁止访问。由于任何程序的实际调用者用户 ID 始终可用，set-user-ID 程序可以采取任何所需措施来确认调用者身份。该机制用于允许用户执行经过仔细编写、调用特权系统入口的命令。例如，有一个只能由“超级用户”调用的系统入口用于创建空目录。如上所述，目录应包含 `.` 和 `..` 项。创建目录的命令由超级用户拥有并设置 set-user-ID 位；它检查调用者创建指定目录的权限后，创建目录并生成 `.` 和 `..` 项。

由于任何人都可以对自己的文件设置 set-user-ID 位，该机制通常无需管理干预即可使用。例如，该保护方案轻松解决了文献 [7] 中提出的 MOO 记账问题。

系统识别一个特殊用户 ID，即“超级用户”，豁免通常文件访问限制；因此例如可以编写转储和重新加载文件系统的程序，而不会受到保护系统的不必要干扰。

### 3.6 I/O 调用

执行 I/O 的系统调用旨在消除各种设备与访问方式之间的差异。没有“随机”与“顺序”I/O 的区分，系统也不强加逻辑记录大小。普通文件大小由写入它的最高字节决定；文件大小既不需要也不可能预先确定。

为说明 UNIX 中 I/O 的要点，下面用一种匿名语言概括若干基本调用，这种语言只表示所需参数，不陷入机器语言编程复杂性。每次系统调用都可能潜在返回错误；为简化起见，调用序列中不表示错误返回。

要读写一个假定已存在的文件，必须先通过如下调用打开：

```text
filep = open(name, flag)
```

`name` 指定文件名，可以是任意路径名。`flag` 参数指示文件是要读、写，还是“更新”即同时读写。返回值 `filep` 称为**文件描述符**，是一个小整数，用于在后续 read、write 或其它操作调用中标识该文件。

要创建新文件或完全重写旧文件，有 `create` 系统调用：若给定文件不存在则创建，若存在则截断为零长度。`create` 也为写入打开新文件，并像 `open` 一样返回文件描述符。

文件系统中没有用户可见的锁，也没有对同时打开一个文件进行读写的用户数量限制。虽然两个用户同时写文件可能导致内容混乱，但实践中不会出现问题。我们认为，在我们的环境中，锁对于防止同一文件用户之间干扰既不必要也不充分。之所以不必要，是因为我们面对的不是由独立进程维护的大型单文件数据库；之所以不充分，是因为普通意义上的锁——阻止一个用户写另一个用户正在读的文件——无法防止例如两个用户都用编辑器编辑同一个文件且编辑器会复制被编辑文件时产生的混乱。

应当说明，当两个用户同时执行诸如写同一文件、在同一目录中创建文件或删除彼此打开的文件这类麻烦操作时，系统有足够内部互锁维持文件系统逻辑一致性。

除下文说明外，读写是顺序的。这意味着如果文件中某个字节是最后一次写入或读出的字节，下一次 I/O 调用隐含指向紧随其后的第一个字节。对每个打开文件，系统维护一个指针，指示下一个要读或写的字节。若读写 $n$ 个字节，指针前进 $n$ 个字节。

文件一旦打开，可以使用如下调用：

```text
n = read(filep, buffer, count)
n = write(filep, buffer, count)
```

在 `filep` 指定文件与 `buffer` 指定字节数组之间，最多传输 `count` 个字节。返回值 `n` 是实际传输字节数。在写情形中，除 I/O 错误或特殊文件物理介质结束等异常外，`n` 与 `count` 相同；但在读情形中，`n` 可以无错误地小于 `count`。如果读指针过近文件末尾，读 `count` 个字符将越过结尾，则只传输足够到达文件末尾的字节；此外，打字机类设备从不返回多于一行输入。当 read 调用返回 $n=0$ 时，表示文件结束。对磁盘文件，这发生在读指针等于文件当前大小时。可以通过依赖设备的转义序列从打字机产生文件结束。

写入文件的字节只影响写指针位置和 count 所隐含的部分；文件其它部分不变。如果最后一个字节超过文件末尾，文件按需增长。

要进行随机（直接访问）I/O，只需把读写指针移动到文件中适当位置：

```text
location = seek(filep, base, offset)
```

与 `filep` 关联的指针被移动到距文件开头、当前位置或文件末尾 `offset` 字节处，取决于 `base`。`offset` 可为负。对某些设备（例如纸带和打字机），`seek` 调用被忽略。返回 `location` 是指针实际移动到的距文件开头的偏移。

#### 3.6.1 其它 I/O 调用

还有若干与 I/O 和文件系统有关的系统入口，这里不讨论。例如：关闭文件、获取文件状态、改变文件保护模式或所有者、创建目录、建立到现有文件的链接、删除文件。

## 4. 文件系统的实现

如 §3.2 所述，目录项只包含关联文件名字和指向文件本身的指针。这个指针是一个整数，称为文件的 i-number（索引号）。访问文件时，其 i-number 用作系统表（i-list）的索引，该表存储在目录所在设备的已知位置。由此找到的项即文件的 i-node，包含文件描述：

1. 所有者；
2. 保护位；
3. 文件内容的物理磁盘或磁带地址；
4. 文件大小；
5. 最后修改时间；
6. 到文件的链接数，即它出现在目录中的次数；
7. 一位，指示文件是否为目录；
8. 一位，指示文件是否为特殊文件；
9. 一位，指示文件是“大”还是“小”。

`open` 或 `create` 系统调用的目的，是通过搜索显式或隐式命名的目录，把用户给出的路径名转换为 i-number。文件打开后，其设备、i-number 和读写指针存储在以 `open` 或 `create` 返回的文件描述符为索引的系统表中。因此，后续 read 或 write 调用中提供的文件描述符，可以轻松关联到访问文件所需信息。

创建新文件时，为其分配 i-node，并建立一个目录项，其中包含文件名和 i-node 号。建立到现有文件的链接，包括创建新名字的目录项、复制原文件项中的 i-number，并递增 i-node 的链接计数字段。删除文件通过递减其目录项指定 i-node 的链接计数并擦除目录项完成。如果链接计数降为 0，则释放文件中的磁盘块，并回收 i-node。

包含文件系统的所有固定或可卸载磁盘空间，被划分为若干 512 字节块，逻辑地址从 0 到依赖设备的上限。每个文件的 i-node 中有 8 个设备地址空间。小（非特殊）文件可放入 8 个或更少块；此时存储块自身地址。对于大（非特殊）文件，8 个设备地址中每一个都可指向一个间接块，该块含 256 个构成文件本身的块地址。因此文件最大可达

$$8\cdot256\cdot512=1,048,576\;(2^{20})\text{ 字节}.$$

上述讨论适用于普通文件。当对 i-node 指示为特殊文件的文件发出 I/O 请求时，后 7 个设备地址字无关紧要，第一个被解释为由两个字节构成的内部设备名。这两个字节分别指定设备类型和子设备号。设备类型指示哪个系统例程处理该设备 I/O；子设备号选择例如连接到特定控制器的磁盘驱动器，或若干相似打字机接口之一。

在这种环境下，`mount` 系统调用（§3.4）的实现相当直接。`mount` 维护一个系统表，键是挂载时指定的普通文件的 i-number 和设备名，对应值是指定特殊文件的设备名。在 `open` 或 `create` 期间扫描路径名时，每出现一个 (i-number, device) 对，就查找该表；若找到匹配，则 i-number 替换为 1（所有文件系统根目录的 i-number），设备名替换为表中值。

对用户而言，文件读写看起来是同步且无缓冲的。也就是说，read 调用返回后数据立即可用；反过来，write 后用户工作区可复用。实际上，系统维护相当复杂的缓冲机制，大幅减少访问文件所需 I/O 操作次数。假设发出一次写调用，指定传输单个字节。UNIX 会检查缓冲区，看受影响的磁盘块当前是否在核心内存；若不在，则从设备读入。然后在缓冲区中替换受影响字节，并登记到待写块列表。写调用此时即可返回，尽管实际 I/O 可能直到稍后才完成。反过来，如果读取单个字节，系统判断该字节所在二级存储块是否已在系统缓冲区；若是，则立即返回该字节；若否，则把该块读入缓冲区并取出字节。

以 512 字节为单位读写文件的程序，比一次读写一个字节的程序有优势，但收益并不很大；主要来自避免系统开销。很少使用或 I/O 量不大的程序，按任意小单位读写都很合理。

i-list 概念是 UNIX 不寻常特性。实践中，这种组织文件系统的方法已证明相当可靠且易于处理。对系统本身而言，其优点之一是每个文件有短而明确的名称，并以简单方式与保护、寻址和访问文件所需信息关联。它还允许非常简单快速的文件系统一致性检查算法，例如验证每个设备上包含有用信息的部分与可自由分配的部分互不相交且合起来覆盖设备空间。该算法独立于目录层次，因为只需扫描线性组织的 i-list。同时，i-list 概念也带来其它文件系统组织中没有的特殊性。例如，谁应为一个文件占用空间付费？由于文件所有目录项地位相等，向文件所有者收费通常不公平：一个用户可能创建文件，另一个用户链接到它，而第一个用户删除该文件；第一个用户仍是文件所有者，但空间应记到第二个用户账上。最简单且较公平的算法似乎是把费用平均分给所有有链接到该文件的用户。当前 UNIX 版本通过完全不收费规避该问题。

### 4.1 文件系统效率

为说明 UNIX 总体效率，尤其文件系统效率，我们对一个 7,621 行程序的汇编计时。该汇编单独运行于机器上；总时钟时间 35.9 秒，速率为每秒 212 行。时间分布为：63.5% 汇编器执行时间，16.5% 系统开销，20.0% 磁盘等待时间。我们不打算解释这些数字或与其它系统比较，只说明我们总体上对系统性能满意。

## 5. 进程与映像

**映像**（image）是计算机执行环境，包括核心映像、通用寄存器值、打开文件状态、当前目录等。映像是伪计算机的当前状态。

**进程**（process）是映像的一次执行。当处理器代表某进程执行时，该映像必须驻留核心；在执行其它进程期间，除非一个活跃的高优先级进程迫使它换出到固定头磁盘，否则它仍留在核心中。

映像的用户核心部分分为三个逻辑段。程序正文段从虚拟地址空间位置 0 开始。执行期间该段写保护，并且同一程序的所有进程共享一份副本。在虚拟地址空间中程序正文段之上第一个 8K 字节边界处，开始一个非共享、可写数据段，其大小可由系统调用扩展。从虚拟地址空间最高地址开始的是栈段，它随硬件栈指针变化自动向下增长。

### 5.1 进程

除 UNIX 引导自身运行时外，新进程只能通过 `fork` 系统调用产生：

```text
processid = fork(label)
```

当某进程执行 `fork` 时，它分裂为两个独立执行的进程。两个进程拥有原核心映像的独立副本，并共享所有打开文件。两个进程唯一不同在于：一个被视为父进程；在父进程中，控制直接从 `fork` 返回；在子进程中，控制转移到位置 `label`。`fork` 调用返回的 `processid` 是另一个进程的标识。

由于父子进程的返回点不同，`fork` 后存在的每个映像都能确定自己是父进程还是子进程。

### 5.2 管道

进程可使用与文件系统 I/O 相同的系统读写调用，与相关进程通信：

```text
filep = pipe()
```

该调用返回文件描述符 `filep`，并创建称为**管道**（pipe）的进程间通道。该通道与其它打开文件一样，通过 `fork` 调用在映像中从父进程传给子进程。使用管道文件描述符的 read 会等待，直到另一个进程使用同一管道的文件描述符写入。此时，数据在两个进程的映像之间传递。两个进程都不需要知道涉及的是管道而不是普通文件。

尽管通过管道进行进程间通信是非常有价值的工具（见 §6.2），但它不是完全通用机制，因为管道必须由相关进程的共同祖先建立。

### 5.3 程序执行

另一个主要系统原语由如下调用唤起：

```text
execute(file, arg1, arg2, ..., argn)
```

它请求系统读入并执行名为 `file` 的程序，并把字符串参数 `arg1, arg2, ..., argn` 传给它。通常 `arg1` 应与 `file` 字符串相同，以便程序确定自己被调用时的名字。使用 `execute` 的进程中所有代码和数据都从文件替换，但打开文件、当前目录和进程间关系不变。只有当调用失败时，例如找不到文件或执行权限位未设置，`execute` 原语才会返回；它更像一条“跳转”机器指令，而不是子程序调用。

### 5.4 进程同步

另一个进程控制系统调用：

```text
processid = wait()
```

使调用者挂起执行，直到它的一个子进程完成执行。然后 `wait` 返回终止进程的 processid。如果调用进程没有后代，则发生错误返回。子进程的某些状态也可用。`wait` 还可能呈现孙进程或更远后代的状态；见 §5.5。

### 5.5 终止

最后：

```text
exit(status)
```

终止进程，销毁其映像，关闭打开文件，并通常彻底清除它。当父进程通过 `wait` 原语得到通知时，指定状态可供父进程使用；如果父进程已经终止，则状态可供祖父进程使用，依此类推。进程也可能因各种非法动作或用户生成信号而终止（见 §7）。

## 6. Shell

对大多数用户而言，与 UNIX 的通信借助一个称为 **Shell** 的程序进行。Shell 是命令行解释器：它读取用户键入的行，并把它们解释为执行其它程序的请求。最简单的命令行由命令名及其参数组成，以空格分隔：

```text
command arg1 arg2 ... argn
```

Shell 把命令名和参数拆分为独立字符串，然后寻找名为 `command` 的文件。`command` 可以是包含 `/` 字符的路径名，用于指定系统中任何文件。如果找到该命令，它被调入核心并执行。Shell 收集的参数可供命令访问。命令完成后，Shell 恢复自身执行，并通过打印提示字符表示准备接受下一条命令。

如果找不到文件 `command`，Shell 会在 `command` 前加上字符串 `/bin/` 并再次寻找文件。目录 `/bin` 包含所有打算供一般使用的命令。

### 6.1 标准 I/O

§3 中关于 I/O 的讨论似乎暗示，程序使用的每个文件都必须由程序自己打开或创建以获得文件描述符。然而，由 Shell 执行的程序一开始就有两个打开文件，其文件描述符为 0 和 1。程序开始执行时，文件 1 已为写入打开，最好理解为**标准输出文件**。除下述情况外，该文件是用户打字机。因此希望写信息或诊断信息的程序通常使用文件描述符 1。反过来，文件 0 一开始为读取打开，希望读取用户键入消息的程序通常读取该文件。

Shell 能够改变这些文件描述符相对于用户打字机打印机和键盘的标准分配。如果命令的某个参数以 `>` 为前缀，则在命令执行期间，文件描述符 1 将指向 `>` 后命名的文件。例如：

```text
ls
```

通常在打字机上列出当前目录中文件名字。命令：

```text
ls >there
```

创建一个名为 `there` 的文件，并把列表放入其中。因此参数 `>there` 表示“把输出放到 there”。

另一方面：

```text
ed <script
```

把 `script` 解释为编辑器命令文件；因此 `<script` 表示“从 script 获取输入”。

尽管 `<` 或 `>` 后面的文件名看起来是命令参数，事实上它完全由 Shell 解释，根本不传给命令。因此每个命令内无需为处理 I/O 重定向编写特殊代码；命令只需在适当处使用标准文件描述符 0 和 1。

### 6.2 过滤器

标准 I/O 概念的扩展，用于把一条命令的输出导向另一条命令的输入。由竖线分隔的一串命令，使 Shell 同时执行所有命令，并安排每条命令的标准输出传给序列中下一条命令的标准输入。例如在命令行：

```text
ls | pr -2 | opr
```

`ls` 列出当前目录文件名；其输出传给 `pr`，后者给输入加上日期标题并分页。`-2` 参数表示双栏。类似地，`pr` 的输出是 `opr` 的输入。`opr` 把输入假脱机到文件以便离线打印。

这一过程也可用较笨拙的方式完成：

```text
ls >temp1
pr -2 <temp1 >temp2
opr <temp2
```

然后删除临时文件。如果没有重定向输入和输出的能力，更笨拙的方法是要求 `ls` 命令接受用户请求，对其输出分页、多栏打印，并安排离线输出。实际上，期望 `ls` 这类命令作者提供如此多样的输出选项，既令人惊讶，而且从效率考虑也不明智。

像 `pr` 这样把标准输入经处理后复制到标准输出的程序，称为**过滤器**（filter）。我们发现有用的一些过滤器可执行字符转译、输入排序以及加密解密。

### 6.3 命令分隔符：多任务

Shell 提供的另一个特性相对直接。命令不必位于不同行，而可用分号分隔：

```text
ls; ed
```

先列出当前目录内容，然后进入编辑器。

一个相关特性更有趣。如果命令后跟 `&`，Shell 在再次给出提示前不等待该命令完成，而是立即准备接受新命令。例如：

```text
as source >output &
```

使 `source` 被汇编，诊断输出进入 `output`；无论汇编持续多久，Shell 立即返回。当 Shell 不等待命令完成时，会打印运行该命令进程的标识。该标识可用于等待命令完成或终止它。

`&` 可在一行中多次使用：

```text
as source >output & ls >files &
```

同时在后台完成汇编和列表。上述使用 `&` 的例子中，都提供了非打字机的输出文件；否则各命令输出会混杂。

Shell 还允许在上述操作中使用括号。例如：

```text
(date; ls) >x &
```

把当前日期时间以及当前目录列表打印到文件 `x`。Shell 也立即返回等待另一请求。

### 6.4 作为命令的 Shell：命令文件

Shell 本身也是一条命令，可递归调用。假设文件 `tryout` 包含：

```text
as source
mv a.out testprog
testprog
```

`mv` 命令把文件 `a.out` 改名为 `testprog`，`a.out` 是汇编器生成的二进制输出，可直接执行。因此若上述三行在控制台键入，source 将被汇编，所得程序命名为 `testprog`，并执行 `testprog`。当这些行位于 `tryout` 中时，命令：

```text
sh <tryout
```

将使 Shell `sh` 顺序执行这些命令。

Shell 还有更多能力，包括替换参数、从目录指定文件子集构造参数表。也可以基于字符串比较或给定文件是否存在来条件执行命令，并在已存档命令序列中执行控制转移。

### 6.5 Shell 的实现

现在可以理解 Shell 操作概要。大多数时候，Shell 等待用户键入命令。当结束一行的换行字符被键入时，Shell 的 read 调用返回。Shell 分析命令行，把参数放入适合 `execute` 的形式，然后调用 `fork`。子进程的代码当然仍是 Shell，它尝试用适当参数执行 `execute`。若成功，将调入并启动名字给定的程序。与此同时，`fork` 产生的另一个进程即父进程，等待子进程死亡。子进程死亡后，Shell 知道命令完成，于是打印提示并从打字机读取另一条命令。

在这个框架下，后台进程实现很简单：只要命令行包含 `&`，Shell 就不等待它为执行命令创建的进程。

幸运的是，所有这些机制与标准输入输出文件概念配合得非常好。进程由 `fork` 原语创建时，不仅继承父进程核心映像，还继承父进程当前打开的所有文件，包括文件描述符 0 和 1。Shell 使用这些文件读取命令行、写提示和诊断信息；普通情况下，它的子进程即命令程序自动继承这些文件。然而当给出带 `<` 或 `>` 的参数时，子进程在执行 `execute` 前，使标准 I/O 文件描述符 0 或 1 分别指向命名文件。这很容易，因为按约定，打开或创建新文件时分配最小未用文件描述符；只需关闭文件 0 或 1，再打开命名文件。由于命令程序运行结束后进程直接终止，`<` 或 `>` 后指定文件与文件描述符 0 或 1 的关联随进程死亡自动结束。因此 Shell 不必知道自身标准输入输出的实际文件名，因为它无需重新打开它们。

过滤器只是标准 I/O 重定向的直接扩展，只是用管道代替文件。

普通情况下，Shell 主循环永不终止。主循环包括 `fork` 返回中属于父进程的分支，即执行 `wait` 然后读取另一命令行的分支。唯一导致 Shell 终止的情况，是在其输入文件上发现文件结束条件。因此，当 Shell 作为带给定输入文件的命令执行时，如：

```text
sh <comfile
```

`comfile` 中的命令将被执行，直到到达文件末尾；随后由 `sh` 唤起的这个 Shell 实例终止。由于该 Shell 进程是另一个 Shell 实例的子进程，后者的 `wait` 将返回，并可处理另一条命令。

### 6.6 初始化

用户键入命令的 Shell 实例，本身也是另一个进程的子进程。UNIX 初始化的最后一步，是创建单个进程，并通过 `execute` 调用一个名为 `init` 的程序。`init` 的作用，是为每个用户可拨入的打字机通道创建一个进程。`init` 的各个子进程打开相应打字机作为输入输出。由于 `init` 被调用时没有打开文件，在每个进程中打字机键盘获得文件描述符 0，打印机获得文件描述符 1。每个进程打印一条要求用户登录的消息，并等待读取打字机回复。开始时无人登录，所以每个进程只是挂起。

最终有人键入姓名或其它标识。相应的 `init` 实例被唤醒，接收登录行，并读取口令文件。如果找到用户名且用户能提供正确口令，`init` 转到用户默认当前目录，把进程用户 ID 设为登录者 ID，并 `execute` Shell。此时 Shell 准备接收命令，登录协议完成。

同时，`init` 主干路径（所有后来成为 Shell 的子实例的父进程）执行 `wait`。如果某个子进程终止，或因 Shell 发现文件结束，或因用户键入错误名字或口令，该 `init` 路径就简单重建已消亡进程，后者重新打开适当输入输出文件并打印另一条登录消息。因此用户只需在 Shell 提示下键入文件结束序列即可注销。

### 6.7 作为 Shell 的其它程序

上述 Shell 旨在让用户完全访问系统设施，因为它会以适当保护模式调用任何程序执行。然而有时需要不同的系统接口，这一点很容易安排。

回想一下，用户通过提供名字和口令成功登录后，`init` 通常调用 Shell 解释命令行。用户在口令文件中的条目，可以指定登录后要调用的程序名以代替 Shell。该程序可自由按任何方式解释用户消息。

例如，某个文书编辑系统的用户口令文件条目指定使用编辑器 `ed` 代替 Shell。因此编辑系统用户登录后，直接进入编辑器并立即开始工作；也可以阻止他们调用不供其使用的 UNIX 程序。实践中，允许从编辑器临时逃逸出去执行格式化程序和其它实用程序是可取的。

UNIX 上若干游戏（如国际象棋、二十一点、三维井字棋）说明了更严格受限的环境。每个游戏在口令文件中都有条目，指定调用相应游戏程序代替 Shell。以游戏玩家身份登录的人，会发现自己被限制在该游戏中，无法探查整个 UNIX 中可能更有趣的东西。

## 7. 陷阱

PDP-11 硬件检测若干程序错误，例如引用不存在内存、未实现指令，以及在要求偶数地址处使用奇数地址。这类错误使处理器陷入系统例程。当捕获非法动作时，除非另有安排，系统终止进程，并把用户映像写到当前目录中的 `core` 文件。调试器可用于确定故障发生时程序状态。

陷入循环、产生不需要输出或用户改变主意的程序，可通过中断信号停止；该信号由键入 delete 字符产生。除非采取特殊动作，该信号只使程序停止执行，不产生核心映像文件。

还有 quit 信号，用于强制产生核心映像。因此意外循环的程序可停止，并在无需预先安排的情况下检查核心映像。

硬件产生故障、中断和 quit 信号，可应进程请求被忽略或捕获。例如 Shell 忽略 quit，以防 quit 把用户注销。编辑器捕获中断并返回命令层。这对停止长时间打印而不丢失正在进行的工作很有用（编辑器操作的是被编辑文件的副本）。在没有浮点硬件的系统中，未实现指令被捕获，浮点指令由软件解释。

## 8. 展望

也许看似矛盾的是，UNIX 的成功很大程度上源于它并非为满足任何预定义目标而设计。第一版是在我们中的一位（Thompson）不满现有计算机设施时写成的；他发现一台很少使用的 PDP-7，着手创造更友好的环境。这项本质上个人的努力相当成功，引起了另一位作者和其他人的兴趣，后来又证明值得购买 PDP-11/20，专门支持文本编辑和格式化系统。当 11/20 又不够用时，UNIX 已证明足够有用，说服管理层投资 PDP-11/45。整个过程中，我们的目标一旦被明确表达，始终是与机器建立舒适关系，并探索操作系统中的思想和发明。我们无须满足别人的要求，对此我们心怀感激。

回顾可见，有三个考虑影响了 UNIX 设计。

第一，由于我们是程序员，自然把系统设计得便于编写、测试和运行程序。我们希望编程便利的最重要表达，是系统被安排为交互式使用，即使最初版本只支持一个用户。我们相信，设计良好的交互系统比“批处理”系统更高产、更令人满意。而且这样的系统相当容易适配非交互使用，反之则不然。

第二，系统及其软件一直受到相当严格的大小约束。在对合理效率与表达能力的部分对立愿望下，大小约束不仅鼓励节省，也鼓励某种设计优雅。这可能是“苦难拯救”哲学的变相版本，但在我们这里奏效了。

第三，几乎从一开始，系统就能够并且确实维护自身。这一点比看似更重要。如果系统设计者被迫使用该系统，他们很快意识到其功能和表面缺陷，并有强烈动机在太晚之前修正。由于所有源程序始终可用且易于在线修改，当新想法被发明、发现或由他人提出时，我们愿意修改和重写系统及其软件。

本文讨论的 UNIX 方面，至少清楚体现了前两个设计考虑。例如文件系统接口从编程角度看极其方便。可能的最低接口层旨在消除各种设备与文件之间、直接访问与顺序访问之间的差别。不需要大型“访问方法”例程来把程序员与系统调用隔离；事实上，所有用户程序要么直接调用系统，要么使用一个只有几十条指令的小库程序，该程序缓冲若干字符并一次读写全部。

编程便利性的另一个重要方面，是没有结构复杂、部分由文件系统或其它系统调用维护并被其依赖的“控制块”。一般而言，程序地址空间内容属于程序自身，我们尽量避免对其内部数据结构施加限制。

鉴于所有程序都应能把任何文件或设备作为输入输出，从空间效率角度把设备相关考虑推入操作系统本身也是可取的。唯一替代方案似乎是：随所有程序装载处理每种设备的例程，这在空间上昂贵；或依赖某种在实际需要时动态链接到适当设备例程的方法，这在开销或硬件上昂贵。

同样，进程控制方案和命令接口已被证明既方便又高效。由于 Shell 作为普通、可换出的用户程序操作，它不消耗系统本身常驻空间，并可以低成本按需要变得强大。特别是在 Shell 作为进程执行并派生其它进程执行命令的框架下，I/O 重定向、后台进程、命令文件和用户可选系统接口等概念，实现起来基本都变得简单。

### 8.1 影响

UNIX 的成功与其说在于新发明，不如说在于充分发掘一组精心挑选的肥沃思想，尤其在于展示它们可以成为实现一个小型而强大操作系统的关键。

`fork` 操作，基本上按我们实现的形式，已存在于伯克利分时系统中。我们在若干点上受 Multics 影响，它启发了 I/O 系统调用的特定形式，以及 Shell 的名字和一般功能。Shell 应为每条命令创建一个进程的想法，也由 Multics 早期设计提示我们，尽管该系统中后来因效率原因放弃了这一做法。TENEX 使用类似方案。

### 9.5 可靠性

我们的可靠性统计比其它统计更主观。以下结果基于我们共同记忆的最佳程度。时间跨度超过一年，使用的是很早期批次的 11/45。

曾发生一次文件系统丢失（五个磁盘中的一个），原因是软件无法应对硬件问题导致的反复掉电陷阱。该磁盘上的文件三天前做过备份。

“崩溃”指非计划的系统重启或停机。大约每隔一天发生一次崩溃；约三分之二由硬件相关问题引起，例如电源跌落和处理器中断到不可解释位置。其余是软件故障。最长不间断运行时间约两周。服务呼叫平均每三周一次，但高度聚集。总正常运行时间约为我们 24 小时、365 天计划的 98%。
